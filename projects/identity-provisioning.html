Identity Provisioning Platform

Built and deployed in an isolated test tenant. Updated November 2026.

The problem

Making onboarding consistent and reviewable

Manual account creation repeats the same naming and attribute decisions for every new starter. I built this lab project to explore how an operator portal can reduce repetitive steps, make proposed changes visible before execution, and keep a request history alongside the directory changes.

The platform builds on my earlier Active Directory automation script. The current MVP implements Entra ID provisioning; a Windows AD or Samba connector remains future work.

Working implementation

From employee details to a disabled account

  1. Sign in with Microsoft Entra ID. Access is restricted to an operator security group.
  2. Enter the employee's name, department and job title. The service generates an available username in the configured verified lab domain.
  3. Review the proposed identity and provisioning steps, then explicitly confirm the request.
  4. Create the Entra account in a disabled state through Microsoft Graph, then check that it exists.
  5. Inspect the result, request status and audit history stored in SQLite.

Engineering decisions

Application, directory and deployment

Application

C# and ASP.NET Core

Razor Pages provide the operator workflow. Separate engine and connector projects keep planning and Microsoft Graph integration apart from the interface.

Traceability

Persistent request history

SQLite stores requests and audit entries. Status changes and their audit entries share a database transaction. Docker volumes retain the database across container recreation.

Deployment

Docker on a Linux VPS

A non-root application container runs behind Traefik with HTTPS and Cloudflare DNS/proxying. Forwarded HTTPS headers are accepted only from the configured trusted proxy.

Evidence and limits

What I tested and learned

I verified account creation in the Entra lab, including a custom verified username domain, and tested access to the VPS-hosted dashboard. The solution also passes 27 automated tests covering core models, planning, state transitions, operator-bound review tokens, concurrent submission, audit transaction rollback, simulated provider failures and trusted-proxy handling.

A key lesson was that a failed provider response does not prove a directory write failed. The workflow flags uncertain execution for investigation rather than automatically repeating account creation.

Next steps

This is a lab MVP. Planned work includes independent lab-target safeguards, stronger approval and plan-integrity checks, verification of the exact created object and disabled state, recovery after interrupted jobs, and an AD-compatible provisioning connector. Group assignment, licensing and secure initial-credential delivery are outside the current implementation.
